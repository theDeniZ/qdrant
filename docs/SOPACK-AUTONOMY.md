# sopack — fully offline and store-agnostic

**Status: M1 done, 2026-09-24 (SOPACK-1.0-PLAN.md's Python-first milestone).**
`sopack/` now makes no store call, no HTTP call and carries no
collection/vector-name at all (enforced by `sopack/tests/test_neutrality.py`);
`sopack/2` (§3.1, §3.2) is implemented end to end — writer, reader, the
committed calibration fixture (`sopack-rs/contracts/e5-large-v1/calibration.json`,
16 entries, generated by the new `python -m app.calibration export` admin
command) and the pack-time self-check. The importer (`app/import_service.py`)
runs the §4 three-step probe for `/2` packs through a new `StoreAdapter`
interface (`app/store_adapter.py`: `QdrantAdapter` + a test-only
`InMemoryAdapter`, proving a `.sopack` imports the same way into a second
backend) and keeps the `/1` live-canary path working unchanged for existing
packs. M2 (the Rust core) is next. Below, the design sketch in §3 is what M1
implemented — no longer "open to change" for what M1 covers, though M2+ may
still refine it.

Related: [IMPORT-PIPELINE.md](IMPORT-PIPELINE.md) (R11, R13),
[IMPORT-PIPELINE-PLAN.md](IMPORT-PIPELINE-PLAN.md) (the current design),
[SOPACK-RUST-MIGRATION.md](SOPACK-RUST-MIGRATION.md), [../sopack/README.md](../sopack/README.md).

## 1. The requirement

> sopack in the future is completely autonomous — no Qdrant connection at all, and
> potentially not even Qdrant alone: I could use ChromaDB if I wanted to.

In concrete terms:

1. **Nothing in sopack connects to a vector store.** `extract → pack → verify` runs
   end to end with the network disabled. The only thing it needs from outside is the
   pinned embedding model in the local cache.
2. **A `.sopack` does not name a vector store.** It carries the book text, payload,
   deterministic ids, vectors and the embedding contract. It does not carry
   collection names, Qdrant named-vector names, Qdrant index types or live point ids
   that the pack depends on.
3. **Everything store-specific lives in the importer**, as one adapter per backend
   (Qdrant today, maybe Chroma later). The same `.sopack` file imports unchanged into
   either one.
4. **R11 still holds.** Nothing is written unless the vectors are proven to be in the
   collection's space. The proof moves to a different place (§3), but the guarantee
   stays.

## 2. Where sopack is coupled to Qdrant today

| # | Coupling | Where |
|---|---|---|
| C1 | `sopack canaries --qdrant URL` scrolls the live collection over HTTP to get reference texts | `sopack/canaries.py`, `cli.py` |
| C2 | The pack's probe refers to **live point ids** + `collection`. It only means something against that one store | `pack.py:295`, `format.py:set_probe` |
| C3 | The manifest's `target` block pins `collection`, `vector_name` (`fast-multilingual-e5-large`, Qdrant/fastembed named-vector naming) and `distance: "Cosine"` (Qdrant's enum spelling) | `contract.check_target` |
| C4 | `Profile.collection` and `Profile.indexes` (`keyword` / `integer` are Qdrant payload-index types) sit in the shared contract | `contract.PROFILES` |
| C5 | Point ids are `uuid5` because Qdrant only accepts UUID/uint ids. They are store-neutral **as strings**, so only the docs and naming need to change, not the ids | `contract.point_id` |
| C6 | The payload is described as "the Qdrant payload", and the `corpus` convention depends on the key being absent (`must_not`) | `book.to_payload`, `contract.PROFILES["sop"]` |
| C7 | Vocabulary: "points", "collection", "live collection" run through the docstrings and the README | throughout |

C1 and C2 are the actual blockers. C3–C7 are about where things live and what they
are called.

## 3. Design sketch

### 3.1 Replace live canaries with a committed calibration fixture

The canary check exists to catch vectors that come out wrong without any visible
error, for example when a pooling change moves every vector into a different space.
The check stays; its reference moves from the live store into the repo:

- **`sopack/calibration/<contract-version>.json`** is committed and versioned with
  `contract.py`. It holds N (≈8–16) entries of
  `{uid, id, text, vector}`, where `vector` is the **stored vector copied from the
  collection** at the moment the fixture was made. The texts are real corpus
  paragraphs, mixed across languages and lengths. At least one should be long enough
  to hit e5's 512-token truncation. Its sha256 becomes part of `contract.EMBEDDING`,
  so a pack declares which fixture it was checked against.
- **At pack time (offline):** `pack` embeds the fixture texts with the same model
  instance that embeds the books, compares them with the fixture vectors, and
  **refuses to build** below the threshold. A broken environment then fails on the
  laptop within seconds, not on the server after a 40-minute pack. The fresh vectors
  still go into the pack as the probe.
- **At import time (importer, model-free):**
  1. *pack ↔ fixture*: cosine of the pack's probe vectors against the importer's own
     copy of the fixture. Both sides vendor the same file, the way they already share
     `contract.py`.
  2. *fixture ↔ store*: fetch the fixture's ids from the target store and compare
     their stored vectors with the fixture's. These should be ≈1.0 for the store the
     fixture was taken from. This catches "this store was built with a different
     contract". Each backend adapter needs only one call for this: get vectors by
     ids.
  3. *Empty store* (for example a fresh Chroma): step 2 has nothing to compare
     against, and the fixture **defines** the store's space. The importer records the
     contract fingerprint on the store (§3.3) at the first import.

  Transitively, pack ≈ fixture and fixture ≈ store gives pack ≈ store. That is the
  same guarantee as today, and sopack never touches the store.
- **Making the fixture** is a one-time maintenance step, repeated only when the
  embedding contract changes. A contract change means a full re-embed and a new
  collection anyway. It reads the store, so it is an **importer-side admin command**
  (today's `canaries.py` scroll logic relocated there), **not** a sopack command and
  not a one-off script (see the no-ad-hoc-scripts rule in IMPORT-PIPELINE.md).

Result: `sopack canaries` and `pack --canaries` are removed. `packs/canaries.json`
keeps working until then.

### 3.2 Split the contract: neutral core vs. store adapters

`contract.py` keeps only what is true for **any** backend:

- the embedding contract (model, library + version, pooling, normalisation,
  `passage:` / `query:` prefixes, dimension, `distance: cosine`, calibration sha)
- per profile: payload schema (required/optional keys, types), identity key, text
  field, id rules, and *hints* for filterable fields (`lang: string`,
  `page: int`), with no backend index types
- id rules: stable string ids (`uuid5(...)`) + the pre-hash uid, both already in
  `points.jsonl`

It drops `collection`, `vector_name` and the Qdrant index types. Those move to the
importer's **adapter config**:

```
profile "sop"   → qdrant: collection=sop,    vector=fast-multilingual-e5-large, indexes{lang:keyword,…}
                → chroma: collection=sop,    space=cosine, …
profile "bible" → qdrant: collection=bibles, …
```

The manifest's `target` block becomes `{profile, contract_version}`.

### 3.3 The importer: one interface, one adapter per store

Roughly what `app/import_service.py` does today, behind an interface:

| Operation | Qdrant | Chroma (future, check against the chosen version) |
|---|---|---|
| ensure collection + indexes | create collection / payload index | `get_or_create_collection`, `hnsw:space=cosine` |
| get vectors by ids (probe step 2) | `retrieve(with_vectors)` | `get(ids, include=[embeddings])` |
| upsert batch | `upsert` | `upsert(ids, embeddings, metadatas, documents)` |
| count / delete by identity key | filter on payload | `where` filter |
| backup before mutation (R2) | snapshot API | no snapshot API. Copy the persistent directory or export |
| contract fingerprint (§3.1 step 3) | importer's own job DB | collection metadata or importer DB |

Things a Chroma adapter must translate, because the pack keeps rich JSON payloads
and flattening is the adapter's job:
- metadata values limited to scalars → `None` (`aligned`, `book_pair`) and lists
  (`aligned`, `bible_refs`) need an encoding
- the `corpus`-key-absent convention for EGW points → an explicit value or an
  adapter-level filter rewrite
- batch size limits and `documents` (the text field) vs. metadata

## 4. Compatibility

- **Pack format:** `sopack/2` for store-neutral packs. The importer accepts
  `sopack/1` (live-canary probe) during the transition so existing packs such as
  `packs/wdys.sopack` still import.
- **Ids do not change.** Same id rules, same uids, so re-importing into the existing
  Qdrant collections updates in place and does not orphan anything.
- **Thresholds:** keep `PROBE_MIN_COSINE = 0.95` as the server floor. Same model and
  same text should score ≈0.9999, so the pack-time self-check can be stricter (0.99)
  without false alarms.

## 5. Acceptance criteria

1. `sopack extract/pack/verify/inspect/doctor` succeed in a container started with
   `--network none` (model pre-cached).
2. `sopack/` contains no store URL, no HTTP client code and no reference to a
   collection or vector name. A test enforces this.
3. `pack` fails fast, before embedding any book, when the calibration check fails
   (for example with pooling forced to CLS in a test).
4. One `.sopack` imports into Qdrant through the adapter with results identical to
   today (same ids, payloads, vectors, and probe passes).
5. The same file imports into a second backend in tests. An in-memory Chroma is
   enough to prove neutrality, even if Chroma never goes to production.

## 6. Order of work

1. Add the importer-side "export calibration fixture" admin command. Generate
   `sopack/calibration/v1.json` from the live `sop` collection and commit it.
2. `pack`: self-check against the fixture, write the probe as fixture-relative.
   Remove the `canaries` command and `--canaries`.
3. Importer: probe steps 1–3. Accept `sopack/1` and `sopack/2`.
4. Split the contract (§3.2) and move the Qdrant specifics into the Qdrant adapter.
5. Put the importer's store calls behind the adapter interface. Add an in-memory
   Chroma adapter for the neutrality test.

The Rust port ([SOPACK-RUST-MIGRATION.md](SOPACK-RUST-MIGRATION.md)) gets simpler once
steps 1–2 are done: an offline sopack needs no HTTP client at all.
